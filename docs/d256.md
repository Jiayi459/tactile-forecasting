# d256 / `Dataset256` — dataset inventory

Release accompanying the ICLR submission page
[iclr-submission-force-vision](https://sites.google.com/view/iclr-submission-force-vision/),
distributed as a single Google Drive zip `d256.zip` (owner `yichenl@mit.edu`, uploaded
2024-11-15, last modified 2025-04-20). The page gives no dataset name, no structure, and no
license; everything below was measured from the archive itself.

**Underlying source is ActionSense** (MIT CSAIL, NeurIPS 2022): the sensor suite, the 20
kitchen activity labels, and the S01–S05 subject codes all match. d256 is a *preprocessed*
derivative — continuous recordings already cut into fixed 16-frame clips — not the raw release.

On CRC: `/users/jhao3/forcevision/Dataset256/`, signals only, verified intact
(80,821/80,821 CRC-32). Fetched with `scripts/crc/fetch_d256.py`; read with `src/d256.py`;
every number here is reproducible via `scripts/probe_d256.py`.

## 2. Directory layout

```
Dataset256/
  signals{,1,2}/<split>/<subject>/<session>/<clip>.p
  signals/ego_4d_verb.npy
  signals/ego_4d_noun.npy
  videos{,1,2}/<split>/<subject>/<session>/video_<clip>_{256,32}.npz
```

Five axes, and no others: **group / split / subject / session / clip**.

**The session directory name *is* `label_idx`.** `signals/val/S05/3/0.p` is class 3,
"Slice a cucumber". Verified on one clip from every class (20/20 match) and re-checkable across
all 80,819 by `probe_d256.py --full`. So a clip's class is readable from its path alone —
which is what makes the counts in §5 possible without unpickling anything.

## 3. Per-clip contents

Each `.p` is a pickled dict, ~163.8–164.1 KB:

```python
{'signal': {...}, 'label_text': 'Slice a cucumber', 'label_idx': 3}
```

`signal` holds nine arrays, all 16 frames leading, schema identical across every clip sampled:

| key | shape | dtype |
|---|---|---|
| `tactile-glove-left` | (16, 32, 32) | float32 |
| `tactile-glove-right` | (16, 32, 32) | float32 |
| `myo-emg-left` | (16, 8) | float64 |
| `myo-emg-right` | (16, 8) | float64 |
| `myo-acc-left` | (16, 3) | float64 |
| `myo-acc-right` | (16, 3) | float64 |
| `joint-position` | (16, 28, 3) | float64 |
| `left-hand-pose` | (16, 24, 3) | float64 |
| `right-hand-pose` | (16, 24, 3) | float64 |

**`signals1` and `signals2` carry a tenth stream, `gaze`; `signals` does not.** Measured on 18
clips spread over cells: 14/14 from `signals1`/`signals2` have it, 0/4 from `signals` do — a
clean group-level split, not a per-clip accident. Confirm exhaustively with
`probe_d256.py --full`, which counts distinct schemas.

Values arrive **already scaled to ~[0,1]** — observed extremes across a 101-clip slice were
`[0, 1]` for EMG and `[0.03, 1]` for the rest. The gloves are **32×32 = 1024 taxels each**.
Note the tactile floor is well above zero (0.13 and 0.40 on that slice), i.e. there is a large
DC pedestal, the same issue OpenTouch's D1 investigated.

> The "256" in `d256`/`Dataset256` is the **video edge length**, not a taxel count. Do not let
> it collide with OpenTouch's 256/169 taxel grids.

Video clips (not fetched): `arr_0` of shape (16, 256, 256, 3) uint8 = 3,145,992 B, or
(16, 32, 32, 3) uint8 = 49,416 B for the `_32` variant.

## 4. Label vocabulary

`signals/ego_4d_verb.npy` — 148 verbs (`pick`, `put`, `drop`, `place`, `hold`, `move`, …)
`signals/ego_4d_noun.npy` — 112 nouns (`hand`, `card`, `cloth`, `bottle`, `bowl`, …)

Ego4D vocabularies, shipped alongside but **not** the label space of the clips themselves —
clips use the 20 ActionSense activities in §5. How the two are meant to relate is undocumented.

## 7. Splits — read this before reporting any val number

| group | train | val | val % |
|---|---:|---:|---:|
| `signals` | 24,955 | 516 | 2.0% |
| `signals1` | 27,691 | 735 | 2.6% |
| `signals2` | 26,456 | 466 | 1.7% |
| **total** | **79,102** | **1,717** | **2.1%** |

There is **no test split**. And `val` is far narrower than "2% of the data" suggests:

| group | val = (subject, class) | clips |
|---|---|---|
| `signals` | S05/2, S05/3, S05/5 | 271, 101, 144 |
| `signals1` | S05/2, S05/4, S05/6 | 303, 329, 103 |
| `signals2` | S05/2, S05/12, S05/14 | 287, 135, 44 |

Three consequences, none of them cosmetic:

1. **`val` covers 3 of 20 classes**, not all 20. A val accuracy is a score on three activities.
2. **The three groups hold out *different* classes.** Only class 2 is common to all three. So
   val numbers from different groups are not comparable to each other.
3. **It is not a subject-held-out split.** S05 supplies val *and* 18,428 clips overall — it is
   the largest subject in train too. The held-out unit is the (subject, session) pair: those
   specific S05 sessions do not appear in train (verified: 0 overlapping session dirs, 0
   colliding clip filenames). So it tests unseen *sessions*, not unseen *people*.

For cross-subject generalization you must build your own split — hold out a whole subject.

## 8. What the three signal groups actually are

They are **not** three independent datasets. They are the same recordings re-windowed at three
temporal strides. Measured by exact frame equality on `train/S01/0/0.p` across groups
(reproduced identically on `tactile-glove-left` and on `myo-emg-left`):

```
signals[i]  == signals1[3i]     i = 0..5      (3x stride)
signals2[i] == signals1[2i]     i = 0..7      (2x stride)
signals[2m] == signals2[3m]     m = 0..5      (consistent: 3/2)
```

So relative sampling stride is **`signals1` : `signals2` : `signals` = 1 : 2 : 3**, all clips
16 frames, meaning each `signals` clip spans **3× the wall-clock duration** of a `signals1`
clip. That also explains the clip counts — the coarser the stride, the fewer 16-frame windows
fit, hence 25,471 < 26,922 < 28,426.

**Therefore: do not pool the three groups and call it 80,819 independent clips.** They overlap
in source material, so a train/val split drawn across pooled groups leaks. Treat one group as
the dataset and the others as alternative temporal resolutions of it.

### Clips are stride-1 sliding windows, and they overlap almost completely

Corrects an earlier reading in this file. `signals` clip 0 and clip 1 share no *identical*
frames, which looks like non-overlapping windows. They are not. Measured on
`signals1/train/S01/0`, clips 0–7, all ten streams:

```
clip c frame j  ==  clip c' frame j'   <=>   c + j == c' + j'
   856 predicted-equal pairs hold, 0 fail, 0 false positives out of 1948 should-differ pairs
```

So **clip `c` is base frames `c … c+15`** — a sliding window of stride **1**. Adjacent clips
share **15 of 16 frames**. `signals` looked non-overlapping only because its stride-3 subsample
lands on a different residue class mod 3 while covering nearly the same span of time.

Every clip index in all 275 cells runs contiguously `0 … N-1`, so the base recording is exactly
recoverable: `base = clip_0's 16 frames + clip_c[15] for c = 1 … N-1`, giving `N + 15` frames.
Verified: every one of the 8 test clips is an exact 16-frame window of the reconstruction, on
all ten streams.

### What this means for how big the dataset really is

| | |
|---|---|
| recordings (one per group × subject × class cell) | **94** in `signals1` |
| unique base frames | **≈ 29,836** |
| recording length | min 36, p10 58, **median 201**, p90 787, max 1068 frames |
| headline "80,819 clips" | **2.7× overcount** in frames; far worse as "independent windows" |

**Consequences that govern any training design:**

1. **A clip-level random split leaks catastrophically.** Neighbouring clips are 15/16 identical,
   so train and val would contain near-duplicates. The only sound split unit is the
   **recording** (subject × class), of which there are 94.
2. **`signals`/`signals2` are not extra data.** They are `signals1` decimated by 3 and 2. Use
   `signals1` as the corpus and reproduce the others with the harness's `downsample` knob —
   the same mechanism `configs/actionsense/eval_harness.yaml` already uses (`fps_raw` 30,
   `downsample` 3).
3. **The 16-frame clip length is not a real constraint.** Reconstructed recordings have a median
   of 201 frames, which is what makes a rolling-origin harness with real history possible at
   all. A 48-frame budget (history + horizon) keeps 87/94 recordings and 25,447 origins.

## 9. Open questions

1. **Sampling rate is unknown and unrecoverable from the data.** Clips carry no timestamps.
   Only the *relative* 1:2:3 stride of §8 is known; the absolute Hz is not. Anything producing
   a physical rate — `causal_velocity(sig, fps)` in `src/opentouch/prob_gru.py:80` — must be
   given a real fps, not one inherited from OpenTouch or EgoTouch. Resolve from the ActionSense
   release or from the authors before any velocity/acceleration feature is trusted.
2. **No license.** The submission page is anonymous and states no terms. Local research use is
   unencumbered in practice; publication or redistribution needs agreement with
   `yichenl@mit.edu`.
3. **How the Ego4D verb/noun vocab is meant to be used** is undocumented (§4).
4. **What distinguishes S05's held-out sessions** — whether they are genuinely separate
   recording sessions or just a slice of one — is not encoded anywhere in the archive.

## 10. Reproducing these numbers

```bash
python scripts/probe_d256.py --root ~/forcevision                    # counts, classes, splits
python scripts/probe_d256.py --root ~/forcevision --full             # + verify all 80,819
python scripts/probe_d256.py --root ~/forcevision --out docs/d256_inventory.csv
```

`--full` re-checks the path-encodes-class invariant on every clip and reports the observed
value range per stream. Structural counts in §1/§5/§6/§7 come from the archive's central
directory and the path walk; §3 and §8 come from unpickling real members.
